## HPROF lifecycle slice — design under investigation
- `HeapDumpParser` explicitly says dump and objects are not thread-safe; callers must externally synchronize. Preserve that contract rather than inventing concurrent read/close safety. `HprofReader#createView` explicitly shares mapping and says closing a view is a no-op. An owned mapping must remain valid through the owning dump lifetime; closing a view must not close the owner. EventIterator/JFR mapping remains unchanged in this slice. Source inspection of `StreamingChunkParser.parse(RecordingStream, ...)` shows it submits chunk tasks and on failure calls `Future.cancel(true)` without waiting for actual worker termination before `parse(Path)` closes its stream. Switching that stream to an owned Arena without first addressing in-flight workers could invalidate buffers while callbacks are still running; actual close/cancellation semantics remain unverified. `EventIterator.close()` drains/polls then joins for at most five seconds and calls parser.close; source does not interrupt a still-alive producer despite its public close Javadoc claiming interruption and termination. This is a source-supported lifecycle risk, not yet reproduced; test with latches and bounded joins before any semantic change. `RecordingStream.close()` currently swallows `IOException` from reader.close, another cleanup-reporting gap to analyze when that path acquires real resources. `StreamingChunkParser.processChunk` catches Throwable and wraps it in RuntimeException; public parse then catches Throwable and wraps in IOException. These are source observations, not yet reproduced behavior regressions; distinguish application Errors and cancellation when designing JFR cleanup. `UntypedJafarParserImpl.run()` creates/closes a new StreamingChunkParser on each call while emitted maps may contain lazy values; `JFRSession` does independent metadata scans and retains a typed parser until session close. JFR mappings therefore cannot simply be closed on each `run`/parse return without defining whether callback values may escape; map lifetime and worker join must be tied to actual caller ownership. `JFRSession` constructor only catches IOException/RuntimeException around metadata scan, and close stops at the first registration failure; these are source-supported partial-failure risks, not yet confirmed. A concrete JFR retention hypothesis: `RecordingStream.threadLocalStreamSlice()` stores a slice retaining `ParserContext`; `ParserContext.storage` retains the original `RecordingStream`, which retains the ThreadLocal key. A long-lived consumer thread can therefore retain value → context → original stream → ThreadLocal key → mapped buffer even after other threads call close. Verify with a real regression/retention evidence before asserting this explains #227; simply clearing contexts could break lazy event resolution.
- Alternatives: reading the whole HPROF into a byte array avoids file locks but destroys large-file/mapped-I/O behavior; JDK-internal Unsafe cleaner is unsupported/restricted. Candidate: an additive explicitly owned scoped-mapping path using Java 25 `FileChannel.map(..., Arena.ofShared())` in the existing buffer abstraction; owner closes the arena, slices are borrowed. Preserve the existing GC-managed JFR map until its lazy-event lifetime is solved. For HPROF and index constructors, close acquired resources on every failure, preserving the original exception and suppressed cleanup errors. HeapDump close must attempt all owned cleanup even after a prior close fails. Small-file and forced multi-splice tests now pass; end-to-end `HeapDumpParser.parse` file cleanup tests were red before implementation and pass afterward. Full coverage and forgotten-close GC behavior remain unverified.
