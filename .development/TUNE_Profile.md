# TUNE_Profile — задание агенту в реальном Java-проекте

**Передайте этот файл агенту, открытому в целевом проекте.** Не нужен доступ к прежней сессии или к исходникам Jafar. Цель — локально подтвердить причину одного измеримого симптома, при разрешении внести минимальное изменение и проверить эффект. Если изменение не доказано, верните диагноз и следующий решающий замер, а не догадку.

## 1. Уточните задачу и границы

1. Прочитайте правила проекта и загрузите `java-performance`. Проверьте рабочий каталог, `git status`, исходный revision, версию JDK **проекта**, команду запуска/теста и разрешённую нагрузку. JDK анализатора не требует миграции проекта.
2. Найдите уже доступные артефакты и сформулируйте одну гипотезу. Нужны симптом, сценарий и метрика: например, p99 запроса, время теста, bytes/op, CPU или рост retained bytes. Если отсутствует воспроизводимый сценарий, запросите именно его либо найдите соответствующий локальный тест. Если разрешён только анализ — не меняйте проект.
3. Контролируйте расходы: сначала короткий репрезентативный запуск, один профиль, одна сводка топ-5–10. Не запускайте все профилировщики, не загружайте файлы в интернет, не включайте резидентный MCP, не добавляйте зависимости или агент в приложение. Не запускайте нагрузку, attach, NMT-перезапуск, heap dump или действия в production без отдельного разрешения; перед дампом проверьте паузу, свободное место, чувствительность и идентичность JVM.

## 2. Выберите маршрут

| Вопрос | Начните здесь | Следующий шаг, если данных мало |
|---|---|---|
| Уже есть native `.jfr`; CPU или аллокации | jvmlens `cpu` / `memory`, компактный JSON | JDK `jfr summary` / `view` для сверки; Jafar `jfr_stackprofile`/граф/точный JfrPath при необходимости |
| GC, блокировка, I/O или латентность | `jfr summary`, потом отчет jvmlens по симптому и размеру окна | Проверка нужных событий через JDK; Jafar `jfr_diagnose` или `jfr_use` для второй гипотезы |
| Исключения, сравнение, граф, точный фильтр | Локальные команды Jafar (`references/expert-tools.md` в skill); `--describe` только для нужного инструмента | `jfr_compare` для двух сопоставимых JFR; не сравнивайте доли с wall-clock |
| Что удерживает память | MAT: histogram → dominators / paths to GC roots → сравнение сопоставимых снимков | `hdump_report`/HdumpPath лишь для точечной эвристики на небольшом дампе; если heap стабилен при росте RSS, рассмотрите NMT |
| Сырые pprof или OTLP **profiles** | Jafar: summary → один query / flamegraph / USE | Уточните типы samples, единицы и labels; счётчик строк не равен сумме весов |
| JVM висит прямо сейчас | `jstall` или разрешённый `jcmd <pid> Thread.print` | Сравните несколько снимков; точное live-состояние — debugger только когда оно нужно |

Все исполняемые пути и примеры лежат в `%USERPROFILE%\.agents\skills\java-performance`. Откройте только `references/local-analysis.md` (jvmlens/JDK/MAT), `references/expert-tools.md` (Jafar) или нужную более узкую справку. Capture — `scripts/jfr-capture.ps1`; измерение изолированных Java-вариантов — `scripts/jfr-bench.ps1` и `references/bench-contract.md`. PowerShell 7:

```powershell
$skill = Join-Path $env:USERPROFILE '.agents\skills\java-performance'
$jf = Join-Path $skill 'profiling\jafar_local.py'
# $rec — разрешённый локальный файл, $before — подходящая базовая запись
& 'C:\Z\JDK\bin\jfr.exe' summary $rec
& 'C:\Z\JDK\bin\java.exe' -Xmx512m -jar 'C:\Z\jvmlens\jvmlens-0.3.1.jar' analyze -r cpu -f json --top-k 5 $rec
python -I $jf --describe jfr_compare
python -I $jf jfr $rec --tool jfr_compare --baseline $before --limit 10
```

Не запускайте команды из примера все подряд: выбирайте по вопросу. Jafar использует установленный официальный `0.29.0` и завершает свой JVM после вызова. Не запускайте `java -jar jfr-mcp…` без `--stdio` (это другой режим). Лаунчер рассчитан на локальные файлы ≤512 MiB каждый и компактный JSON ≤1 MiB. По умолчанию 60 с; один дополнительный запуск с более узким запросом допустим после анализа причины; для большого heap используйте MAT и собственные согласованные лимиты. Для MAT сначала подтвердите файл и HPROF-заголовок, подготовьте приватные scratch/диск; проверяйте отчёт, не только код выхода.

## 3. Измерьте, исправьте, перепроверьте

1. Подготовьте повторяемую нагрузку и сравнимые условия: JDK/флаги, ввод/БД, прогрев, конкуренция, набор данных, длительность и равный объём работы. Сохраните baseline до изменения. По возможности выполните ≥3 измеренных запуска на вариант; сравните медиану и разброс, absolute и relative, не только сэмплы.
2. Проверьте, что в профиле есть интересующие события, окно попало в работу, а система не ограничена посторонним процессом. Пустое событие может означать выключенную настройку, порог, недостаточную длительность или ошибку чтения. Суммируйте веса аллокаций, сопоставьте горячий путь с первым релевантным вызовом проекта. Отделяйте `suspect` от подтверждённого роста и пути удержания. Известные ограничения конкретной версии — `references/known-issues.md`; например, Jafar TSA 0.29.0 может сводить разные потоки в один.
3. Измените один доказанный механизм в **целевом** репозитории только в рамках разрешения. Напишите проверку корректности; запустите узкие тесты и согласованную регрессию. Проверьте ту же нагрузку до/после и побочные метрики (p99, ошибки, GC, RSS, throughput — что релевантно). Не ослабляйте тесты и не коммитьте артефакты. Если эффект тонет в шуме или данные несопоставимы, вердикт `INCONCLUSIVE`; не включайте оптимизацию только потому, что профиль выглядит лучше.
4. Запишите `performance-report.md` в приватном каталоге задачи: симптом и цель; версия/ревизия, сценарий и команды без секретов; валидность запусков; значения по запускам, единицы, медиана/разброс; гипотеза, источник в коде и подтверждение; изменения и фактические проверки; вердикт и ограничения. Сырые JFR/HPROF/профили, JVM args/properties, payload и строки объектов держите локально и не включайте в репозиторий или чат. Отвечайте ссылкой на отчёт и несколькими решающими числами.

## 4. Что сделать, если проблема в инструментарии, а не проекте

- **Неверная команда/приоритет в skill:** воспроизведите на безопасном примере и исправьте одну каноническую инструкцию под `java-performance`, если вам разрешено менять общий skill. Не размножайте рекомендации по файлам. Перепроверьте новую команду на установленной версии и сценарий, где skill не должен вызываться.
- **Баг/нехватка Jafar:** зафиксируйте выпуск, команду, ожидаемый и наблюдаемый минимальный результат на синтетике, последствия и обход. Запишите находку в `java-performance/profiling/bug_report.md` или `feature_request.md` рядом с установленной утилитой. Если править общий skill нельзя, положите запись в отчёт. Клон Jafar для этого не нужен. Не ждите upstream, если jvmlens/JDK/MAT уже отвечают на вопрос. Не публикуйте issue, не правьте общие настройки и не push без разрешения именно на это действие.
- **Новый кейс/ограничение масштаба:** соберите измерения времени, памяти, объёма и пригодности результата. Предлагайте доработку только если она закрывает реальный повторяемый сценарий. При ошибке, неправильном ответе, orphan JVM или небезопасном побочном действии остановите эту ветку анализа и явно сообщите владельцу.

**Готово**, когда другой человек может повторить измерение, понять, почему выбран этот инструмент, и отделить доказанный эффект от предположения. Не держите сессию или профилировщик открытыми ради передачи результатов.




**What I'd do before calling it finished for agent use**
========================================================

- One real-workload drill on a non-trivial app: capture CPU, allocations and a heap dump; analyze with MAT and jvmlens; write the report. That validates scale and the whole loop.
- Automate at least one successful capture and one successful bench in tests, not just validation paths.
- Add a "check your environment" command/step that verifies paths, jar hashes, and fixture counts before an agent starts, so failures are caught before analysis.
- Gradle/Maven capture modes and live attach to a real workload are unverified end to end. Attach worked against my 20-second toy JVM; that's not the same as a Spring service.

Bottom line: the goal "give agents a large, working profiling toolset with a skill that explains it" is achieved. The goal "this is production-ready for arbitrary Java workloads" is not yet proven. If agents will use it on small-to-medium local artifacts and follow the routing, it will do real work today. If it's expected to carry weight on multi-GB heaps or flaky live services, treat this as a beta until the drill above is done.
