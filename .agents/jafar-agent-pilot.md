## What the review found

1. **Must fix before committing the HPROF slice:** [HeapDumpImpl.java:411–420](../hdump-parser/src/main/java/io/jafar/hdump/impl/HeapDumpImpl.java#L411-L420) publishes the optional offset reader before opening the data reader. An `IOException` from the second open nulls both fields without closing the first. With scoped arenas the now-unreachable owner can leave its mapping allocated. Header validation is not a guard against a later open failure; the progress callback runs after validation and before this pair opens. This is a source-proven leak path; an executable reproduction is still needed. The data reader's constructor cleanup only releases its own mapping.
2. **Must fix for machine output:** The real JAR produced JSON plus a human footer. [Shell.java:1181–1218](../jafar-shell/src/main/java/io/jafar/shell/unified/Shell.java#L1181-L1218) also treats query text as shell syntax, takes the limit after evaluation, and uses a renderer that [writes arbitrary `Number` text directly](../jafar-shell/src/main/java/io/jafar/shell/unified/Shell.java#L1651-L1680). Nonfinite numbers are not valid JSON. Do not trim the footer, interpolate raw input into `script`, or advertise `--limit` as a memory/work bound. Also don't substitute a bare evaluator for projected `show` paths and silently return whole events instead.
3. **Java 25 migration is incomplete as a release:** Toolchain declarations now target 25 in the reviewed Gradle files, but active workflows and docs still assume older runtimes. The [PR workflow](../.github/workflows/pr-tests.yml#L421-L469) still labels runtime cells 8/21 even though `test8` now runs on 25. Lombok and Error Prone are present in only three module build files (`llm-openai`, `pprof-parser`, `jfr2pprof`). Do not ship or publish the migration as complete, or infer CI compatibility from local Gradle configuration.
4. **Legacy JFR close still fails on Windows:** The mapped-reader close is ineffective; the current producer/failure paths do not establish that all workers and escaped lazy values are finished. See [StreamingChunkParser](../parser-core/src/main/java/io/jafar/parser/internal_api/StreamingChunkParser.java), [EventIteratorImpl](../parser-core/src/main/java/io/jafar/parser/impl/EventIteratorImpl.java#L188-L235), and [#227](https://github.com/btraceio/jafar/issues/227). This blocks a claim about persistent server or library cleanup; it need not block a pilot whose actual child JVM has exited and whose recording is independently movable on Windows.

## Changes to the old plan

- **Pilot comes before broad parity, not before correctness.** Fix the concrete HPROF leak if accepting that slice; then build the smallest machine path. Don't tie the pilot to resolving the public JFR lifetime contract, every upstream issue, or finishing every lint migration. Those remain explicit separate deliverables, not waived requirements. If the broad mixed working tree cannot be checkpointed cleanly, keep it intact; use an owner-authorized isolated pilot branch from a known baseline or ask before publishing any branch with unresolved material verification.
- **Direct dispatch beats script wrapping.** A fixed trusted script is fine for manual demos; appending a query or removing output banners is not a stable adapter. Direct entry points for all ~37 MCP tools up front cost more and introduce untested parity claims. Start with one machine command and a small supported matrix.
- **One consultation, one manual code review, one decisive test per failure class.** ChatGPT was consulted in GPT-6 High mode via a temporary, unpersonalized chat using a generic scenario (no repo contents or user data). It recommended strict versioned stdout, no interpolation into script grammar, and proving consumer completion and process termination independently. Its answer informed the design; it did not see or verify code. Prior DeepSeek work was reviewed against actual source and XML by the lead.

## Stop rule, token budget, and eventual cutover

Ship the first useful slice after A–C gates, not after every row in D. If a format does not pass, withhold it explicitly and keep MCP; ask the owner if that drops below the useful pilot scope. Prioritize the next issue by wrong-result/safety impact, then real blocked workflows from feedback, then measured cost. Reuse one implementer context and compact receipts; resolve named failures with focused tests, batch expensive runs at slice boundaries, and run only one manual adversarial integration review per materially changed slice. Use small projections/aggregates in agent output. If actual token savings matter, compare two identical workflows before and after with the same model/input and provider-reported input/output/cache usage; don't invent savings from file size.

Persistent MCP cutover is a separate owner decision. Compare the real installed MCP tool list, required query/analysis payload semantics, failure behavior and supported workflows against the new path (including cross-session/large data workflows where users need them). Preserve the MCP artifacts, settings and other clients. Rehearse re-enabling the exact prior DSH entry through a safe configuration mechanism, then consider disabling only that selected DSH registration. Do not read raw credential-bearing profiles, stop borrowed JVMs, or push/release. If a required use case lacks verified parity or rollback, stay in opt-in mode.
